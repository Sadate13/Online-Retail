# Model Card : ciblage des codes promo (risque de non-réachat à 30 jours)

> D'après Mitchell et al. (2019), *Model Cards for Model Reporting*. Les chiffres sont ceux du README, des slides et de l'application (`python -m backend.train`).

| Rubrique | Contenu |
|---|---|
| **Usage prévu** | Aider le responsable marketing à choisir, chaque mois, à quels clients actifs envoyer un code de réduction de 10 £ : le modèle donne pour chaque client la probabilité qu'il ne rachète rien dans les 30 jours. L'humain garde la main sur le budget et l'envoi. |
| **Usages à éviter** | Exclure ou pénaliser un client (le score ne sert qu'à **offrir** un code) ; l'appliquer aux achats sans numéro client ou à des clients inactifs depuis plus de 90 jours ; l'utiliser sur une autre période ou un autre commerce sans réentraîner et revalider ; présenter le gain espéré comme un gain mesuré. |
| **Modèle** | Régression logistique (scikit-learn, `max_iter=1000`, `random_state=42`) dans un `Pipeline` : variables numériques imputées par la médiane, avec indicateur de valeur manquante, puis standardisées ; pays et catégorie principale en one-hot. Une forêt aléatoire et un gradient boosting donnent une AUC proche (environ 0,74) : le modèle le plus simple et le plus lisible est gardé. |
| **Données** | Online Retail (UCI) : 2 592 clients actifs au 9 novembre 2011, 28 variables (récence, fréquence, montants, activité sur 30 et 90 jours, parts par catégorie, pays, annulations). Split stratifié 80 / 20 (2 073 clients pour l'entraînement, 519 pour le test), graine 42. Voir `data_quality_card.md`. |
| **Baseline** | **Envoyer le code à tous** les clients actifs, ce qu'on ferait sans modèle : gain espéré de −720 £ sur les 519 clients du test. Référence de classement : la règle « dernier achat » (trier par jours depuis le dernier achat) : AUC 0,61. |
| **Performances** | **Test** (519 clients jamais vus) : AUC 0,75, contre 0,61 pour la règle « dernier achat » et 0,50 pour le hasard. **Validation croisée** en 5 parties sur l'entraînement : AUC 0,73 ± 0,02. **Métrique métier** : gain espéré de +310 £ avec le modèle, contre −720 £ en envoyant à tous ; 224 codes envoyés au lieu de 519 ; 76 % des clients contactés ne rachètent effectivement pas, contre 57 % sur l'ensemble. |
| **Décision** | Le code est envoyé si la probabilité de départ dépasse **67 %**. Calcul : un client qui allait partir et reçoit le code est retenu 30 % du temps et rachète pour 50 £, soit 15 £ récupérés en moyenne ; le code coûte 10 £. Envoyer est rentable si p × 15 > 10, donc p > 10 / 15 = 0,667. Le seuil vient de ce calcul, **pas** d'un réglage sur le test. Pour comparaison, le seuil qui maximise le gain sur l'entraînement est 0,62, proche. Les trois hypothèses (10 £, 50 £, 30 %) sont réglables dans l'application, qui recalcule le seuil. |
| **Variables importantes** | Importance par permutation sur le test (baisse de l'AUC quand on mélange la variable) : 1) nombre de jours d'achat différents (−0,10), loin devant 2) le délai moyen entre deux achats (−0,02), 3) le nombre de factures, au total et sur 90 jours (−0,01 chacun). Le pays et la catégorie principale comptent peu (−0,005). Lecture métier : un client qui achète régulièrement revient ; un client d'une seule commande part 8 fois sur 10. **Une variable importante n'est pas une cause** : le modèle repère des clients à risque, il n'explique pas pourquoi ils partent. Plusieurs variables se ressemblent (nombre de factures, nombre de jours d'achat) : leurs coefficients se compensent et ne se lisent pas un par un. |
| **Équité** | Aucune variable d'âge, de sexe ou d'origine. Le **pays** est utilisé. Vérification sur le test : les clients hors Royaume-Uni partent un peu plus (61 % contre 57 %) mais reçoivent moins souvent un code (31 % contre 44 %) ; parmi ceux qui partent, 48 % sont ciblés contre 58 % pour les clients britanniques. Ce constat repose sur **51 clients étrangers seulement** : il est fragile. **À faire** : suivre ces taux par pays pendant le pilote, et tester un modèle sans la variable pays (elle pèse peu dans les performances). |
| **Limites** | Testé sur une seule période, le mois avant Noël 2011, très particulier. Le coût du code, l'achat futur et le taux de réussite sont des **hypothèses** : le modèle prédit qui part, pas qui le code fera rester (il faudrait un modèle d'uplift et une campagne test). Test sur 519 clients : le gain peut varier de plusieurs dizaines de livres d'un tirage à l'autre. 25 % des ventes sans numéro client sont exclues. 5 192 lignes en double (1,3 %) ne sont pas retirées ; les retirer donnerait +295 £ au lieu de +310 £. Les données ont plus de 10 ans. |
| **Maintenance** | Réentraîner chaque mois avec les ventes du mois écoulé (`python -m backend.data` puis `python -m backend.train`), et relancer les tests (`python -m pytest`). Indicateurs à suivre pendant le pilote : taux de réachat des clients ciblés contre un groupe témoin sans code, gain réel par code envoyé, part des ciblés par pays. Alerte si l'AUC mesurée sur le mois passé descend sous 0,65, ou si le gain réel par code est négatif deux mois de suite. |
